总体建议
你这套方案可以保留5 个Phase 的结构，但底层概念建议改成：

Landscape = 已有研究地图
Gap = 有证据的缺口
Novelty = 与已有研究不同
Contribution = 为什么这种不同有理论价值
不要把它们混成一个innovationScore。

1. Phase 1 建议：数据底座要更“证据化”
1.1 theoryBackbone 不建议只存一个字符串
一篇论文可能同时用：

索尔
塔姆
信托转移
准社会互动
建议结构改成：

理论骨架：[ 
  {
    id ："行" ， 
    标签：“刺激-机体-反应” ， 
    evidenceText : " ... " , 
    置信度：0.82​ 
  }
]
这样后面做“理论整合”更可靠。

1.2 statedGap 不一定在摘要里
很多论文的gap 不在abstract，而在introduction。建议字段叫：

声明的差距：[ 
  {
    文本：” ... ” ， 
    sourceSection : "摘要|引言|讨论" , 
    gapType : "背景|机制|边界|理论|结构|结果" , 
    置信度：0.7​ 
  }
]
不要只存一个字符串。

1.3 studyContext 很重要，要更细
建议：

studyContext : { 
  行业：字符串| null ，   
  country ：字符串| null ，   
  人口：字符串| null ，   
  sampleType ：字符串| null ，   
  方法：" SEM " | " PLS- SEM " | "实验" | "调查" | "定性" | "综述" | null             
  platformOrSetting ：字符串| null ，   
  objectType ："人类" | "人工智能" | "虚拟影响者" | "平台" | null         
}
你的业务里“AI 主播vs 真人主播”这种context gap 很关键。

2. ConstructRelationship 表建议调整
你设计的表很好，但建议改几个字段。

2.1 relationship 和 sign 分开
现在：

关系：正相关|负相关|调节|调解 
建议拆成：

关系类型：直接|中介|调节​​​​​     
符号："正" | "负" | "混合" | "未知"       
因为“调节”本身也可能有正/负调节。

2.2 supportingPapers 不要只放 paperIds
建议每条支持证据里包含：

支持证据：[ 
  {
    paperId ，
    hypothesisId ，
    陈述，
    效果大小，
    年，
    理论骨干，
    studyContext ，
    方法
  }
]
否则后面无法解释：

这条边来自哪些论文？什么情境？什么方法？是否稳健？

2.3 innovationScore 名字建议改
你的算法：

100 - min ( 100 , totalOccurrences * 15 )     
本质上衡量的是：

这条关系是否被研究得少
不是创新性本身。

建议命名为：

探索不足的分数
或者：

饱和度得分
新颖性潜力
因为低频不等于创新，高频也不等于没价值。

例如：

“天气→ 购买意愿”低频，但可能没理论价值。
“信任→ 购买意愿”高频，但在AI 主播场景中可能有context gap。
3. 最大风险：不能把“少见”当成“创新”
这是你方案里最需要调整的地方。

创新性应该至少由四个维度组成：

Innovation = 差异性× 研究价值× 理论合理性× 证据支撑
建议模型评分拆成：

指标	含义
新奇得分	与已有文献不同
差距匹配度得分	是否回应明确gap
证据评分	是否有文献依据
理论一致性得分	理论逻辑是否顺
贡献分数	是否能形成论文贡献陈述
最终再合成一个：

创新准备度评分
不要只靠关系出现次数。

4. Phase 2 建议：模型输出字段很好，但要更明确
你设计的：

贡献声明：{ 
  已知信息，
  缺什么，
  whatThisAdds ，
  间隙类型
}
非常对。

我建议再加两个字段：

researchGapClaim ：字符串 
理论贡献：字符串 
因为论文写作中常用表达是：

尽管之前的研究表明……，但人们对……知之甚少。
本研究的贡献体现在……
系统应该直接帮用户生成这类句子。

建议结构
贡献声明：{ 
  whatIsKnown ：字符串， 
  whatIsMissing ：字符串， 
  whatThisAdds ：字符串， 
  whyItMatters ：字符串， 
  gapTypes ：字符串数组， 
  贡献类型："上下文" | "理论"    | "机制" | "边界" | "结构" | "结果"       
}
5. edgeNoveltyTags 设计要调整
你现在设计：

“衍生品” | “新颖的” | “矛盾的” | “边界”      
建议增加：

“转移”
“机制插入”
“ modified_extension ”
“理论嫁接”
因为很多博士论文创新不是“完全新边”，而是：

把旧关系迁移到新情境
在旧关系中插入新中介
给旧关系增加边界条件
用新理论解释旧关系
建议改成：

edgeNoveltyTags ：
-饱和 
-未充分探索 
-已转移上下文 
-新中介者 
-新版主 
矛盾的 
- theory_extension 
6. Phase 2 的硬拒规则要小心
你写：

noveltyScore < 25 → 硬拒
这个有风险。

因为有些论文模型创新点不在边本身，而在：

新情境
新样本
新方法
新理论整合
新调节机制
比如：

信任 → 购买意愿
这条边很常见，但放到“AI 主播+ 算法透明度+ 拟社会互动”场景下仍可能有价值。

建议不要只按edge novelty 硬拒，而是：

如果edgeNovelty 低，但contextGap/theoryGap/boundaryGap 高，则允许通过。
可以改成：

如果 （
  新颖性评分< 25   且
  gapFitScore < 50   &&
  innovationTypes .长度===  0
）拒绝 
7. Phase 3 文献全景视图非常重要
我很支持你加：

热图
方面
差距
集群
但我建议页面不要只是“可视化”，而要直接服务生成模型。

每个gap 后面应该有按钮：

基于这个gap 生成模型
例如：

Gap: 现有研究多关注真人主播，AI 主播情境不足
[生成情境迁移模型]
或者：

Gap: 信任→ 购买意愿已饱和，但缺少拟社会互动机制解释
[生成机制揭示模型]
这样Landscape 页不是报表，而是模型创新入口。

8. 你Phase 1 的触发时机建议改一下
你写：

变量提取完成自动跑
论文新增/删除时增量跑
建议：

变量提取完成后：自动rebuild
论文删除后：标记landscape stale，异步rebuild 或用户手动rebuild
论文新增但未抽取变量：不要 rebuild，因为没有关系数据
批量抽取时：不要每篇都rebuild，一批结束后rebuild 一次
否则会重复计算。

9. 共享 canonicalize 是对的，但建议升级
你说：

变量名一定要走canonicalize()
对，但现在仅字符串规则不够。

建议分三层：

rawName: "对 AI 直播者的信任感知"
canonicalName: "trust"
contextQualifier: "AI streamer"
构建家庭：“信任”
这样系统可以知道：

trust 是大构念
trust in AI streamer 是具体情境变量
trust in platform 是另一个对象
否则会把不同trust 全部合并，导致误判。

10. 我建议你增加一个Phase 0：定义创新分类标准
在动代码前，先把6 类创新变成严格判定表。

例如：

创新类型	判断条件	证据来源
情境迁移	关系高频，但当前topic context 未覆盖	研究背景 + 主题
机制揭示	高频X→Y 中插入低频mediator	构建关系
边界发现	高频X→Y 加入moderator	构建关系
理论整合	模型使用两个以上理论cluster	理论主干
矛盾解决	signConflict=true	关系表
构念延展	新构念连接高频核心构念	规范构造统计数据
这个判定表是整个系统“精准性”的灵魂。

11. 推荐调整后的施工顺序
我建议顺序稍微改一下：

Phase 1：Landscape 数据底座
保留你的方案，但改名：

构建关系
PaperContext
纸理论
PaperGap
景观元数据
第二阶段：间隙分析仪
先做gap，而不是先改模型生成。

因为模型生成应该基于gap。

输出：

差距：[ 
  {
    类型，
    描述，
    证据，
    推荐的创新战略
  }
]
第三阶段：差距驱动模型生成
模型生成输入不再只是userPrompt，而是：

选定的 GapId
选定的创新战略
第四阶段：贡献感知模型卡
展示：

已知信息
缺什么
该模型增加了什么
新颖性得分
贡献声明
第五阶段：人工智能助手集成
让AI 助手围绕gap 讨论：

你想突出情境创新，还是机制创新？
而不是泛泛问“你想生成什么模型”。

12. 一句话评价你的方案
你的方案已经抓到了正确方向：用关系知识库和文献全景来支撑创新性生成。
但我建议把“创新性”从单一低频分数升级为：

已有研究共识+ 明确gap + 理论合理的新组合+ 可写成贡献陈述
这样系统生成的模型才不会只是“少见”，而是“有论文价值”。
